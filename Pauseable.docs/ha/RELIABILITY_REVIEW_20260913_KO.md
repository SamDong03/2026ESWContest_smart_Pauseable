# 실제 운용을 위한 보강과 남은 과제

작업일: 2026-09-13. **사용자 요청에 따라 Pi에 연결하거나 배포하지 않고 로컬에서 수정·검증했다.** 실제 가전 상태, 개인 모델, HA 설정은 바꾸지 않는다.

## 현재 단계에 대한 판단

기존 구현은 수집 -> baseline -> 30일 조건 -> IF/AE 학습 -> 저장/재로드 연결을 확인한 연구용 시제품이다. 하지만 자동 실행된다는 것과 실제 행동을 빠짐없이 수집하고 신뢰할 만한 경보를 낸다는 것은 다르다.

이번에는 새로운 모델이나 데이터를 무작정 늘리기보다, 누락·실패가 성공/정상처럼 보이지 않도록 운영 조건과 검사 도구를 보강했다. 치매 진단, 모든 가전의 완전한 이벤트 수집, 제품 수준 안전성을 확보했다고 주장하지 않는다.

## 수정한 문제

| 문제 | 이전 동작/위험 | 이번 변경 |
|---|---|---|
| baseline 누락 | 특징만 생성하고 종료 코드 0. 탐지까지 성공한 것으로 오해 가능 | 파일 존재·구조·유한 통계값 검사 후 시작. 없거나 잘못되면 명시적 실패 |
| 과거 산출물 | 고정 결과 이름 때문에 지난 결과를 이번 결과로 읽을 가능성 | 주기별 run_id, 완료 표시, 행 수·필수 열·중복 검사. 통과한 주기만 cursor 전진 |
| 수집 대상 | 이름 키워드에 의존하고 어떤 가전이 빠졌는지 불명확 | 정확한 entity_id 지정/제외 옵션, 필수 엔티티 누락/불가용 목록 |
| 불완전 이력 | HA 연결 자체와 가전 이벤트 완전성이 혼동될 수 있음 | 관찰 보고서에 두 의미를 구분. 필수 상태의 직전 2시간 이력이 없으면 학습 제외 |
| 설정 변경 | 다른 대상/기준을 쓰면서 기존 개인 이력·모델을 재사용할 위험 | 가구·baseline 해시·선택 목록을 상태 디렉터리에 기록. 달라지면 기존 이력을 보존하고 새 디렉터리 요구 |
| 초기 스냅샷 | 초기 목록 요청 도중 받은 최신 이벤트를 이후 도착한 오래된 스냅샷이 덮을 위험 | 해당 요청 중 이벤트가 있었던 엔티티는 뒤늦은 스냅샷으로 덮지 않음 |
| AE 미수렴 | 200회 반복 종료 경고가 있어도 경보율 기준만 통과하면 자동 적용 가능 | 최대 1,000회로 한도 조정, 실제 반복/손실/수렴 여부 기록. 경고가 남으면 활성화 거부 |
| 잘못된 모델 값 | NaN 임계값 등에서 비교식이 모두 거짓이 되어 정상처럼 보일 위험 | 임계값 순서·유한성, 양수 scale, 가중치/층 크기 검사 후 추론 |
| 결합 경보 | 승격 과정에서 기존 이유가 지워지거나 점수가 낮아질 수 있음 | 기존 규칙 이유에 모델 이유를 추가하고 기존 높은 점수 유지 |
| 운영 상태 | 긴 분석 중 상태 갱신이 없고 수집 자식 장애 복구가 늦어질 수 있음 | 약 15초 상태 기록, 수집 자식 재시작 backoff, 분석 타임아웃/중단 시 자식 종료 |

학습 반복 수를 늘렸다고 반드시 수렴하거나 더 정확해지는 것은 아니다. 정상 가정 holdout 경보율 15% 이하 조건도 유지한다. 미수렴 모델은 연구용 비교 점수를 볼 수 있지만 자동 lifecycle 활성화는 거부한다. 기존 활성 묶음에 기록된 미해결 학습 경고가 있으면 baseline fallback으로 전환하도록 했다.

공개 임상 연구 전용 trainer의 400회 설정과 이전 53개 미수렴 실험을 이번에 재학습/덮어쓰지는 않았다. 공용 HA/전력 trainer 변경으로 앞으로 새 실험 수치가 달라질 수 있으며, 과거 보고서는 당시 결과로 보존한다.

## 2초 냉장고 문 열림을 어떻게 확인하나

`src/audit_ha_events.py`를 추가했다. HA 원본 CSV를 읽는 오프라인 도구이며 HA/SSH에 접속하거나 가전을 조작하지 않는다.

```sh
python src/audit_ha_events.py --input outputs/door_trial.csv --entity-id binary_sensor.test_fridge_door --expected-opens 3 --from-time 2026-09-13T12:00:00+09:00 --to-time 2026-09-13T12:05:00+09:00 --output outputs/door_trial_audit.json
```

위 파일명과 엔티티는 예시다. 나중에 실제 수집 원본과 실제 entity_id로 실행한다. 가전 시험을 하지 않았다면 `--expected-opens`를 생략한다. 이때 결과는 성공이 아니라 `not_measured`다.

보고 내용:

- open/close 이벤트 수, 짝이 맞는 구간, 2초 이내 구간.
- 초기 스냅샷과 동일 원본 중복은 열림 횟수에서 제외.
- 닫힘만 있는 구간, 닫힘 없는 열림, 중간 unavailable 표시.
- HA의 event_time과 CSV recorded_at 차이. 이 값은 가전 -> 클라우드 -> HA 지연을 포함하지 않는다.
- 사용자가 실제로 관찰한 기대 횟수와 기록 횟수의 일치 여부.

**닫힘만 기록됐다고 사라진 열림을 만들어 넣지 않는다.** HA의 열림/닫힘 시각 차이가 2초라는 것과 물리적으로 정확히 2초 열렸다는 것은 다르다. 실제 시험은 2초·5초·10초 열림을 각각 여러 번 시행하고, 독립적으로 적은 시각/횟수와 HA/Pi 기록을 대조해야 한다. 횟수만 같아도 완전 수집을 증명하지는 못한다.

현재 LG ThinQ 공식 설명은 일반 상태 변경 이벤트와 구형 모델의 5분 갱신을 구분한다. 실제 장치의 전달 특성은 현장 시험으로 확인해야 한다. [LG ThinQ 갱신 설명](https://www.home-assistant.io/integrations/lg_thinq/#data-updates)

## 명시적 수집 대상과 안전한 이력 분리

연속 서비스와 수집기/파이프라인에 다음 옵션을 추가했다.

```text
--entity-id binary_sensor.my_fridge_door
--entity-id sensor.my_washer_current_status
--exclude-entity-id sensor.retired_appliance_current_status
--baseline models/user_001_real_baseline_v2.json
```

- `--entity-id`를 하나라도 주면 그 목록만 선택하고 모두 필수 관찰 대상으로 취급한다.
- 지정하지 않으면 기존 키워드 선택 방식이 유지된다. 제외는 자동으로 판단하지 않고 사용자가 명시해야 한다.
- 필수 목록과 제외 목록이 겹치면 오류다. 실제 사용 중인 고장 엔티티를 경보를 없애려고 제외하면 안 된다.
- 필수 상태가 관찰 구간 시작 전부터 확인되지 않거나 unavailable이면 학습 조건을 만족하지 못한다.
- 엔티티 이름을 지정한다고 mapper가 모르는 가전의 의미가 자동으로 생기지는 않는다. 매핑과 실제 신호 의미를 별도로 확인해야 한다.

연속 서비스의 상태 폴더에는 `runtime_identity.json`을 만든다. 가구, baseline 내용, 필수/제외 엔티티, 선택 키워드가 바뀌면 새 상태 폴더를 요구한다. 기존 SQLite나 모델은 자동 삭제·합병하지 않는다.

**기존 Pi의 runtime/local을 그대로 새 코드로 실행하면 미확인 legacy identity 때문에 중단될 수 있다.** 나중에 배포할 때 기존 데이터를 백업·보존한 채 새 상태 폴더에서 시작하거나, 이력의 수집 조건을 검토한 명시적 이관 절차가 필요하다. 이번에는 자동 이관이나 Pi 서비스 파일 적용을 하지 않았다.

## 상태를 확인하는 방법

```sh
python src/check_ha_runtime.py --state-dir runtime/local
```

로컬 파일만 읽는다. 상태가 없거나 오래됐거나 저장공간/관찰 문제가 있으면 종료 코드 2와 원인을 반환한다. 정상 운용 증거가 있으면 0이다. 디렉터리가 없다고 빈 정상 상태를 만들어 주지 않는다.

| 표시 | 의미 |
|---|---|
| websocket_unconfirmed | HA 연결 확인 기록이 없거나 40초보다 오래됨 |
| supervisor_status_stale | 감독 프로세스의 상태 기록이 없거나 120초보다 오래됨 |
| incomplete_observation | 선택 가전 관찰 이력 부족. 학습 가능과 다름 |
| low_disk / critical_disk | 각각 여유 512MiB / 64MiB 미만 |
| invalid_artifacts | 이번 run_id의 탐지 결과를 확인하지 못함. 이력 cursor를 넘기지 않음 |
| configuration_error | baseline 또는 상태 이력/대상 조건이 잘못됨 |
| rejected / training_failed | 모델 활성화 안 함, baseline 유지 |

`status=ok`는 해당 주기 처리 성공이다. `normal`은 행동 규칙 결과다. `active`는 모델 lifecycle 상태다. 서로 다른 의미이며, 어느 것도 치매가 없다는 뜻이 아니다.

Linux의 분석 자식 프로세스는 별도 프로세스 그룹으로 실행하고 중단/900초 초과 시 정리한다. Windows에서는 해당 helper의 종료/회수 동작을 시험하지만 ATLAS의 실제 systemd·프로세스 그룹 동작 검증을 대신하지 않는다.

## 의도적으로 하지 않은 것

- 실제 센서 이벤트가 없는 것을 합성 정상 자료로 채우기.
- 다른 가정/공개 자료의 모델을 개인 모델로 교체하기.
- 가전 자동 제어, 도어락 잠금/해제, 외부 보호자 알림 전송.
- 실제 데이터를 확인하지 않고 특정 임계값을 의료적 기준으로 정하기.
- 원본 데이터·Docker 이미지·개인 이력을 자동 삭제해서 공간 확보하기.
- 실제 Pi 재부팅, 네트워크 장애, 한 달 운용 시험을 로컬 시험으로 대체했다고 주장하기.

## 다음 작업 우선순위

1. **입력 검증:** 실제 가전 2/5/10초 이벤트 시험, 각 엔티티의 갱신 특성·클라우드 지연·불가용 원인 확인.
2. **운용 검증:** 저장공간 확보, 새 버전의 Pi 단계적 배포, 물리 재부팅/재연결과 수집 이력 연속성 점검.
3. **정상 데이터 검토:** 실제 생활에서 정상/의심 구간과 가전 점검·외출 등의 상황 기록. 자동 baseline 선별은 정상 정답이 아님.
4. **독립 성능 평가:** 날짜/가구를 분리해 놓치는 행동, 하루 경보 횟수, 경보까지 지연을 평가. 모델 수를 늘리기보다 오탐 원인을 분석.
5. **사용자 경험:** 보호자 알림 채널·전송 동의·중복 억제·확인/해제 흐름 결정 후 구현. 현재 10분 분석은 즉각적인 안전 경보 용도가 아님.
6. **임상/대회 요구:** 실제 가전·치매 원자료 승인/확보, 전문가 평가 및 C++/.ipk 요구사항의 공식 확인.

로컬 검증 결과와 변경 파일 목록은 같은 작업의 `outputs/ha_reliability_20260913` 보고서에 기록한다. 과거 GitHub/Pi 검증 기록은 그대로 보존한다.
