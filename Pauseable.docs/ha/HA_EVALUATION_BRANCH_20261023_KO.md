# HA 비교 실험 검증용 브랜치 작업 기록

## 1. 이번 요청과 범위

요청은 GitHub 브랜치를 확인하고, 브랜치를 쓰는 이유를 설명하며, 분리할 만한 작업을 새 브랜치에 올리는 것이었다. 따라서 이미 main에 반영한 HA 기능이나 보고서를 이전 상태로 되돌리지 않았다.

- 기준 커밋: `6abb4505bc6d1dc421c244b97388d0a867f777eb`
- 새 브랜치: `codex/ha-evaluation-hardening`
- 범위: 보고서 전용 비교 도구, 회귀 시험, 해당 시험의 GitHub Actions, 이 설명 문서
- 제외: 운영 탐지 기준, IF/AE 학습 코드·가중치, Central·Flutter·TTS 운영 코드, Pi 설치, 제출용 PPT/PDF 수정

## 2. 브랜치는 왜 사용하는가

`main`은 팀이 합친 기준 버전이다. 브랜치는 그 버전에서 출발해 새 변경을 별도 커밋으로 쌓는 작업 경로다. 프로젝트 폴더를 GitHub에 통째로 한 번 더 복사하는 개념이 아니라, 커밋을 가리키는 이름이다.

예를 들어 main의 결과를 유지하면서 평가 검증을 보강하고 싶다면, 새 브랜치에서 수정하고 시험한다. GitHub에 push하면 다른 팀원이 변경 내용을 볼 수 있다. Pull Request(PR)는 그 차이를 검토하고 main에 합칠지 결정하는 요청이다. 브랜치에 올리는 것과 main에 병합하는 것, Pi에 배포하는 것은 서로 다른 작업이다.

이번 브랜치를 만들었다고 이미 main에 있는 HA 코드와 보고서가 사라지거나 이 브랜치로 이동하는 것은 아니다. 이번 추가 변경만 분리된다. 합쳐진 뒤에도 브랜치 이름은 남을 수 있으므로, 이름이 보인다는 이유만으로 미반영 코드라고 판단하면 안 된다. squash 병합은 커밋 ID도 달라질 수 있어 PR의 병합 여부를 함께 확인해야 한다.

## 4. 왜 이번 작업을 새 브랜치로 골랐는가

최근 보고서는 Baseline과 IF/AE 결합의 효과뿐 아니라 정상 맥락 경보 증가도 보여준다. 이 비교를 앞으로 다른 자료로 반복할 때 입력이 잘못 맞춰지면 알고리즘 차이처럼 보일 수 있다. 그래서 운영 성능을 임의로 조정하기보다, 비교 자료가 맞는지 실패를 명확히 알리는 검증을 별도 개선 대상으로 골랐다.

이는 새로운 치매 진단 기능이나 검출 성능 향상 작업이 아니다. 이미 저장된 결과를 재현하는 과정의 신뢰성을 보강하는 작업이다.

## 5. 무엇을 어떻게 바꿨는가

### 시각과 행 대응 검증

이전 `variants()`는 바로 운영 `combine()`을 호출했다. 이 함수의 left join은 모델 시각이 빠져도 규칙 행을 남길 수 있다. 이번 보고서 도구에서는 먼저 특징·규칙·모델 점수가 같은 시각의 같은 행인지 확인한다.

새 `validate_alignment()`는 빈 자료, 시각 열 누락, 시각 누락·파싱 실패, 중복, 역순, 서로 다른 키·행 순서를 거부한다. 판정 등급의 오타와 잘못된 관측 완전성 마스크도 비교 전에 거부한다. 숫자를 임의로 채우거나 시각을 추측해 맞추지 않는다.

날짜의 파싱은 유효성과 정렬 확인에만 쓴다. 실제 결합은 원래 `window_end` 키를 사용하므로, `12:05:00`과 `T12:05:00Z`처럼 표기가 다르면 같은 순간처럼 보여도 조용히 합치지 않는다.

### 최적화 모드에서도 유지되는 재현 검사

기존에는 저장 결과와 재생 결과의 일치를 Python `assert`로 확인했다. `python -O`에서는 assert가 제거된다. 이제 `require()`와 `require_reproduction()`이 조건을 확인하고 다르면 `ValueError`로 중단한다. Baseline 표본 수·P95 일치와 관측 불완전 사례의 보류 확인도 같은 방식으로 바꿨다.

최적화 Python을 자식 프로세스로 실제 실행하고, 서로 다른 판정에 대해 종료 코드가 실패인지 확인하는 시험을 추가했다. 운영 임계값이나 결합 정책을 바꾼 것은 아니다.

### 시간축과 입력 추적

이전 냉장고 시간축은 `0, 1, 2, ...`인 행 번호였다. 현재 동결 자료는 1분 간격이므로 숫자가 맞지만, 중간 시각이 빠진 다른 자료에서는 잘못된 분 단위 표시가 될 수 있다. `elapsed_minutes()`로 실제 시각 차이를 계산하도록 바꿨다. 예를 들어 12:00, 12:05, 12:06은 0, 5, 6분이다.

정상 대조군의 `month/month_features.csv`도 출처 SHA-256 목록에 추가했다. 기존 출처 해시를 바꾸는 것이 아니라 누락된 비교 입력 한 파일을 추가 추적한다.

### 자동 시험

보고서 시험은 기존 16개에서 29개가 됐다. 추가 13개는 빈 자료·누락·중복·역순·잘못된 시각, 서로 다른 결합 키, 등급 오타, 실제 경과 시간, 재현 성공·실패, 최적화 모드의 검사 유지를 다룬다.

새 `ha-report-checks.yml`은 관련 PR과 main 변경에서 일반 Python과 `python -O`로 이 시험을 실행한다. 기존 Flutter/알림 CI는 수정하지 않았다. 저장소 읽기 권한만 사용하며 배포·모델 학습·MQTT 발행·가전 제어를 하지 않는다.

## 6. 검증 절차

기존 HA 연구 Docker 이미지의 Python 3.12 환경에서 저장소를 읽기 전용으로 연결하고, 네트워크 없이 실행한다. 새 소스는 읽기 전용 연결된 저장소에서 불러온다.

```bash
python -m unittest discover -s Pauseable.docs/evaluation/ha/checks -v
python -O -m unittest discover -s Pauseable.docs/evaluation/ha/checks -v

python Pauseable.docs/evaluation/ha/compare_baseline_models.py \
  --source-root /path/to/verified-output \
  --output-dir /path/to/new-empty-output
```

전체 재생에는 이전 제출 점검에서 보존한 합성 month/fridge/evidence 산출물을 사용했다. 개인 자료나 새 학습은 사용하지 않았다. 새 산출물은 별도 빈 디렉터리에 만들며 기존 보고서와 동결된 결과는 덮어쓰지 않았다.

| 확인 | 결과 |
|---|---|
| 일반 Python 단위 시험 | 29개 통과, 건너뛰기 없음 |
| `python -O` 단위 시험 | 29개 통과, 건너뛰기 없음 |
| 냉장고 단일·반복 사용 재생 | 기존 판정 재현 |
| 별도 합성 사례 96개 × 4구성 | 상세 CSV 384행이 기존 파일과 바이트 단위로 일치 |
| 비교 JSON의 판정·분포·시점 | 기존 수치와 구조적으로 일치 |
| 기존 입력 출처 해시 | 모두 유지; 정상 대조군 특징 파일 1개 추가 |

384행 CSV의 SHA-256은 `318ce9596285918aa1ab016ff736e7e2f5a172fcc60c5fe5ceffec190c7927ba`다. 냉장고 첫 주의는 Baseline / IF 추가 / AE 추가 / 결합 순으로 26 / 26 / 5 / 5분을 유지했다. 반복 가설 경보는 16 / 18 / 24 / 24개, 정상 맥락 경보는 22 / 28 / 30 / 30개이며 정상 대조군 718개는 모두 정상이다. 결과가 좋아 보이도록 임계값을 바꾸지 않았다.

처음 JSON을 문자열로 대조했을 때 새 경과 시간의 `0.0`과 기존 `0` 같은 직렬화 차이 때문에 불일치가 보고됐다. 숫자가 달라진 것으로 결론 내리지 않고 JSON으로 파싱한 구조적 비교와 상세 CSV의 바이트 대조로 재확인했다. 지표는 같았고, 추가한 출처 해시 외의 수치 변화는 없었다.

이 브랜치에서 다시 실행한 단위 시험은 보고서 관련 29개다. 이전 운용 시험 184개나 Pi 실장비 시험을 이번에 새로 실행한 것으로 표시하지 않는다. GitHub Actions 설정 추가와 원격 실행 성공도 구분하며, 원격 실행 여부는 PR의 Checks에서 확인한다.

## 7. main에 합치기 전 읽어야 할 한계

입력 검증을 강화해도 합성 자료가 실제 치매환자 자료가 되는 것은 아니다. 동일한 특징의 정상 사용·반복 가설은 여전히 구분할 수 없다. 정상 맥락 경보나 실제 Pi·가전 종단 시험의 한계를 해결했다고 주장하지 않는다.

이번 변경을 main에 합치려면 PR의 파일 차이와 시험 결과를 확인한 뒤 병합한다. 브랜치 업로드만으로 Pi의 코드가 교체되거나 실행되지는 않는다.
