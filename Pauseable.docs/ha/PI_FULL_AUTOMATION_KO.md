# Pi 전체 자동 운용: 2026-09-11 변경 사항

## 현재 확인한 범위

- Pi `172.20.10.2` SSH 접속, ARM64(aarch64) 실행을 확인했다.
- Pi에서 기존 Home Assistant와 Mosquitto는 실행 중이었다. HA 주소는 `http://127.0.0.1:8123`이다.
- PC와 Pi에서 최종 회귀 테스트 58개가 통과했다.
- Pi에서 합성 30일 데이터 생성 → 특징 생성 → 정상 구간 선별 → IF/AE 학습 → 검증 → 모델 저장/적용을 실행했다.
- 다른 Pi 컨테이너 프로세스에서 모델을 다시 읽고 추론했다. 모델 손상, 출처 불일치, 관찰 부족을 차단하는 시험도 통과했다.
- 실제 HA의 읽기 전용 수집과 수정된 파이프라인 완료를 확인했다. 가전 제어 명령은 보내지 않았다.
- **재접속 후 새 자동 시작 서비스 전환을 완료했다.** `ha-docker-engine.service`, `ha-ai-full.service` 모두 `active/running`, `enabled`를 확인했다.
- 새 서비스에서 실제 HA 수집, baseline 분석, SQLite 저장 성공을 확인했다. AI 서비스를 재시작해도 HA/MQTT 프로세스는 유지됐으며 이력도 이어졌다.
- 실제 600초를 기다려 두 번째 주기 처리도 확인했다. 21:34 → 21:44(KST) 구간 처리 후 특징/판정 이력이 2행에서 12행으로 늘었고 SQLite 무결성 검사를 통과했다.
- AI 컨테이너만 종료하는 복구 시험도 통과했다. systemd 자동 재시작 횟수가 0 → 1로 증가했고 HA/MQTT의 시작 시각과 PID는 유지됐다. 복구 후 22:09(KST)까지 분석, 두 DB 이력 37행 및 최종 압축 쓰기를 확인했다.
- 원래 `/data/ha_ai` 서비스와 모델은 보존했다. 백업은 새 배포 폴더의 `deployment_backup`에 있다.

## 바뀐 흐름

```text
HA WebSocket 수집 (계속 실행)
          ↓
주기별 원본 스냅샷 → 정규화 → 1분 단위 행동 특징
          ↓
baseline 규칙 탐지 + 관찰 누락 표시
          ↓
출처·가구·특징 버전을 확인하여 SQLite 이력에 저장
          ↓
30개 유효 관찰일 충족? → 아니오: baseline 유지
          ↓ 예
시간순 학습/보정/검증 → Isolation Forest + Autoencoder
          ↓
검증 실패: 모델 적용 안 함, baseline 유지
검증 통과: 새 모델 버전을 저장하고 활성 포인터를 원자적으로 교체
          ↓
baseline + 학습 모델 탐지, 재시작 후 모델 자동 로드
```

`run_ha_full_service.py`가 수집 프로세스와 분석 프로세스를 분리한다. 학습 중에도 수집은 계속된다. 시작 후 첫 분석은 약 60초 뒤, 그 이후에는 이전 분석이 끝난 후 600초 뒤 실행한다. 분석에 걸리는 시간만큼 실제 간격은 10분보다 조금 길다. 각 주기 안에서는 1분 간격의 특징을 계산한다.

## 자동 학습 조건

단순히 가장 오래된 날짜와 최근 날짜가 한 달 차이라고 학습하지 않는다.

- 가구 ID, `source_type`, 특징 버전이 같아야 한다.
- 학습에 사용할 각 특징의 직전 2시간에 확인된 WebSocket 관찰이 있어야 한다.
- 하루에 최소 12개의 서로 다른 시간대에서 유효한 정상 후보 특징이 있어야 한다.
- 이런 날이 30일 이상 있어야 한다. 관찰 누락이 있으면 달력 기준 한 달보다 오래 걸릴 수 있다.
- 기본 학습 함수는 사람이 검토한 정상 구간만 허용한다.
- 배포용 `--allow-screened-training`은 baseline 정상 판정 구간을 자동 후보로 허용하는 명시적 옵션이다. `baseline_screened`로 기록하며, 사람 검토 데이터인 것처럼 표시하지 않는다.
- 학습은 최대 6,000행으로 시간순 표본을 제한한다. 이력은 45일 보관한다.

baseline이 놓친 이상행동이 자동 후보에 섞일 수 있다. 따라서 자동 선별은 정상 정답을 보장하지 않는다. 기존 baseline 자체를 자동 덮어쓰는 기능은 켜지 않았다.

## 모델과 최종 판정

- IF: 기존 scikit-learn 구현, 트리 128개.
- AE: 기존 `MLPRegressor` 구현, 은닉층 16 → 6 → 16. 입력을 복원하도록 실제 가중치를 학습한다.
- 표준화기는 학습 구간에만 맞춘다. AE 가중치는 JSON, IF는 체크섬을 기록한 신뢰된 로컬 joblib로 저장한다.
- 시간순 60/20/20 분할과 120분 이상의 간격을 적용한다. 보정 구간의 95/99 분위수로 attention/risk 기준을 정한다.
- 정상 가정 검증 구간의 IF 또는 AE 경보 비율이 15%를 넘으면 적용을 거부한다. 이 기준은 운영 시험용 상한이지 제품 수준 정확도 인증이 아니다.
- `shadow`에서는 모델 점수만 기록한다.
- 배포용 `hybrid`에서는 한 모델의 경보는 attention, 두 모델이 모두 risk이면 risk로 올릴 수 있다. baseline의 기존 경보를 낮추지 않는다.
- 모델이 없거나 손상됐으면 baseline으로 돌아간다. 관찰이 부족할 때 baseline도 정상인 구간은 `unknown`으로 남긴다.
- 모델 적용은 점수 계산에만 영향을 준다. 실제 도어락·전자레인지 등을 자동 조작하는 코드는 추가하지 않았다.

## 수집과 데이터 처리 수정

1. 초기 상태 목록을 기다리는 동안 도착한 HA 이벤트도 처리한다.
2. 에어컨 상태 문자열이 같아도 목표 온도·팬 모드가 바뀌면 수집한다.
3. 에어컨의 전원/모드/온도/팬 신호를 분리하고, 같은 엔티티 안에서도 신호별 전이 횟수를 센다.
4. 식기세척기에도 세탁기·건조기와 같은 완료 후 재시작 규칙을 연결했다.
5. 미확인 출처·다른 가구·누락 특징을 모델에 넣지 않는다.
6. WebSocket 확인 구간과 가전 `unavailable`을 따로 다룬다. 프로세스가 오래 켜져 있었다는 이유만으로 관찰 완료라고 하지 않는다.
7. CSV에서 빈 이유/패턴 열이 숫자로 읽히는 pandas 자료형 문제를 수정했다.
8. 누적 특징과 판정은 SQLite에 저장한다. 매 주기마다 한 달 분량 CSV 전체를 다시 쓰지 않도록 했다.
9. SQLite 안의 JSON 행을 무손실 zlib 압축한다. 기존 비압축 행과 새 압축 행을 함께 읽을 수 있고, 기존 이력을 삭제하거나 다시 쓰지 않는다. 합성 행 모양을 반복한 저장량 시험에서 45일 예상 크기가 약 294MiB에서 60MiB로 줄었다. 이는 특징/판정 DB의 추정치이며 HA 자체 DB, 로그, 모델 파일은 별도다.

HA의 핑/퐁과 이벤트/결과 메시지 처리는 [공식 WebSocket 문서](https://developers.home-assistant.io/docs/api/websocket/)를 확인했다. HA 연결이 살아 있어도 제조사 클라우드가 신호를 빠뜨리는 것까지 증명할 수는 없다.

## 실제 시험 결과

첫 Pi 가속 시험은 합성 HA 원본 788행, 특징 720행이었다. 30일을 빨리 시험하기 위해 **특징 끝점을 60분 간격**으로 계산했으며, 실제 운영의 1분 간격과 동일한 장시간 부하 시험은 아니다. 시스템 시계는 바꾸지 않았다.

- 29일째: `collecting`, 학습 모델 미적용.
- 30일째: 실제 학습 후 `active`.
- 원본 생성부터 모델 적용까지 Pi에서 약 58초. 최종 압축 SQLite판 재시험은 약 62초.
- 정상 가정 내부 검증 구간의 IF/AE 합집합 경보 비율: 12.5%.
- 학습에 넣지 않은 이후 4일, 96개 특징으로 추가 시험했다.
- 주입한 전자레인지 반복 사용 이상 구간 2개 중 2개에 모델 경보가 있었다.
- 독립 시험의 정상 주간 구간 경보 비율: 약 11.1%.

**이는 자동 운용 연결 시험의 통과다. 실제 가정의 탐지 정확도, 의료적 성능, 여러 이상행동 유형에 대한 성능 증명이 아니다.** 합성 모델은 실제 가구 저장소에 복사하지 않았다. 공개 UK-DALE/REFIT 모델도 이번 개인화 모델로 사용하지 않았다.

## 현재 남은 문제

- Pi HA의 비가상 선택 항목은 15개였으며, 변환 가능한 상태는 냉장고·건조기·세탁기에서 읽혔다. 실제 물리 가전의 전체 연결 완료를 뜻하지는 않는다.
- 식기세척기·공기청정기 및 일부 세탁기/건조기 항목 7개가 `unavailable`이었다. 이 구간은 학습 대상에서 제외한다. 가전 연결 복구 또는 사용하지 않는 항목의 명시적 제외가 필요하다.
- `/data`는 약 94% 사용 중이며 현재 여유는 약 340MiB다. 기존 이미지를 재사용했으며, 원래 파일이나 Docker 이미지를 삭제하지 않았다. 여유 공간 64MiB 미만에서는 보호를 위해 새 학습/수집을 중단한다. 저장 압축을 해도 HA와 다른 프로그램의 디스크 증가까지 막지는 못하므로 저장공간 확인은 필요하다.
- 이 Pi 커널은 Docker 메모리 제한을 지원하지 않는다는 경고를 냈다. Python 운영 프로세스에는 별도로 주소 공간 1GiB 제한을 설정했고 BLAS 스레드를 1개로 제한했다. 실제 메모리 사용량 제한과 주소 공간 제한은 다르다.
- 물리 전원 재부팅 시험, 한 달 실시간 내구 시험, 실제 정상 가구 모델 검증은 아직 하지 않았다.
- `.ipk`/ARC/C++ 앱으로 포팅한 작업이 아니다. Pi 내부 Docker/Python 경로를 시험했다.
- PC/Windows VM 없이 Pi에서 실행되지만 인터넷이 필요 없는 구성은 아니다. 현재 실제 가전은 LG ThinQ 통합이며 [공식 문서](https://www.home-assistant.io/integrations/lg_thinq/)상 LG 클라우드 연결과 인터넷이 필요하다.

## 배포 경로

- 신규 코드: `/data/ha_ai_fullcycle_20260911`
- 실제 운영 이력: `runtime/local/models/history.sqlite3`
- 실제 운영 판정 이력: `runtime/local/decisions.sqlite3`
- 최종 합성 시험 모델: `outputs/month_compressed/synthetic_models`
- 활성 모델 포인터: 각 모델 저장소의 `active.json`
- 수집 로그: `runtime/local/collector.log`
- 최근 분석 로그: `runtime/local/last_pipeline.log`
- 학습 단계 로그: `runtime/local/models/lifecycle.jsonl`

등록한 서비스는 `ha-docker-engine.service`와 `ha-ai-full.service`다. 기존 AI 서비스가 자식 프로세스로 띄웠던 Docker 엔진을 독립 systemd 서비스로 옮겼다. 기존 AI 단위에는 전환 시 엔진을 강제 종료하지 않도록 `KillMode=process` drop-in을 적용했고, 기존 단위는 중지 및 부팅 자동 시작 해제했다. 엔진에는 정상 종료 신호를 보낸 뒤 새 단위로 기동했다.

ATLAS의 `/`는 기본 읽기 전용이다. 서비스 설치와 부팅 등록 동안만 임시로 쓰기를 허용한 뒤 `sync` 및 읽기 전용 복구를 완료했다. 기본 부팅 옵션과 `/etc/fstab`은 변경하지 않았다.

## 운영 확인

다음은 **Pi SSH 터미널**에서 실행하는 읽기 전용 확인 명령이다.

```sh
systemctl is-active ha-docker-engine.service ha-ai-full.service
systemctl is-enabled ha-docker-engine.service ha-ai-full.service
docker ps
cat /data/ha_ai_fullcycle_20260911/runtime/local/service_status.json
```

- `status=ok`: 해당 분석 실행이 오류 없이 끝났다는 뜻이다. 모든 가전 상태가 정상이라는 뜻은 아니다.
- `collector_running=true`: 수집 프로세스가 살아 있다는 뜻이다. WebSocket 확인 시각도 함께 검사한다.
- `data_quality=incomplete_observation`: 시작 직후 2시간 이력이 부족하거나 선택한 가전 항목이 unavailable인 경우다.
- `learning_status=collecting`, `eligible_days=0`: 개인화 모델에 쓸 유효 관찰일을 모으는 중이다. 현재 가전 unavailable 문제가 지속되면 이 숫자는 늘지 않는다.
- `models/active.json`이 없는 것은 초기 단계에서 정상이다. 합성 시험 모델로 이 파일을 대신 채우지 않는다.

현재 기본 흐름은 최초 개인화 모델을 한 번 자동 학습하고 유지한다. 이후 주기적 재학습이나 새로운 생활패턴으로 자동 덮어쓰기는 이번 배포에 포함하지 않았다.
